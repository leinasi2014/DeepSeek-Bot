## 二、解冻后第一件事：P3，且必须先跑测试

**入口条件**：全量测试全绿之前，不得安装、不得合并进 `dev`。

原因是一个具体的风险点：`ds-bot/src/host/memory.js` 里 `reviewBatch` 原有三处自动合并残骸（引用 `bot` / `sessionId` / `room`，而它们都不是该函数的参数），解冲突时改成了 `keeper` / `next()` / `name`。**这三处是运行时符号，`node --check` 和静态扫描都查不出作用域错误。**

好在现有测试正好覆盖：`memory.test.js` 的 `three unreadable reviews in a row give the batch up, with the lines kept` 会走进那个分支，改错必 `ReferenceError`。

**报数顺序（缺一项不算通过）**：

1. `npm test` 全量结果行（pass / fail 总数）；
2. `memory.test.js` **77 pass / 0 fail**，且这两条用例**名字出现在清单里**：
   - `three unreadable reviews in a row give the batch up, with the lines kept`
   - `a keeper out of the group during the review keeps the place, and the next keeper reads the lines again`
   这个名字检查是要紧的：**通过数对不代表目标分支被执行**；
3. `memory.test.js` 的 skipped 计数必须是 **0**（该文件里没有 `t.skip`/`test.skip`，出现 skipped 即异常）；
4. 群复查前后 `memory/team/MEMORY.md` 的 sha256 一致；
5. `reviewed.json` 新键是 `group:<room>`，旧 `group:<room>:<bot>` 数量不变。

其余门（`harness` 先装、lint 0 error、mock smoke 无 skipped）按 runbook §3.1 走。**`build` 与 `build-client --check` 已在 P2 完成，解冻后不必重跑**，除非之后又改了 `src/client/`。

## 五、两条要带走的经验

1. **自动合并成功 ≠ 正确。** 三个残骸都出现在 `git merge` 说 "Auto-merging" 的地方，没有冲突标记。验收不能只看 `<<<<<<<` 归零。
2. **`ROOM_LATE_ROUNDS` 这类数值我们和上游各改一次，取值不同。** 现在仓库里是 **1000**（我们的值），上游 `v0.2.0` 是 10。这次没冲突（上游没改这个文件），但下次若上游也改，会冲突——**遇到时保我们的 1000**，理由是我们需要长派活链。
